# OPSFORGE: Data architecture

## 1. Stores and their roles

| Store | Role | Source of truth | Backed up |
| --- | --- | --- | --- |
| PostgreSQL 17 with pgvector | Structured data, embeddings, job state, outbox, audit | Yes | Yes |
| Object storage (S3 API; MinIO locally) | Uploaded files, generated artifacts | Yes, for bytes | Yes |
| Redis | Queue broker, pub/sub, short-lived cache, shared rate-limit counters | **No** | No |
| Browser storage | Cache, offline copy, and the legacy home of modules not yet moved | No once a module is on the API | No |

One principle decides placement: **if losing it would lose user progress, it is in PostgreSQL or object storage.** Redis can be flushed at any time with no data loss, only a delay (jobs are re-enqueued from their database state, section 8).

Local containers: `opsforge-postgres` (pgvector pg17, volume `opsforge_postgres_data`) and `opsforge-redis` (volume `opsforge_redis_data`) are **built**. An `opsforge-minio` service is **designed**.

## 2. PostgreSQL schema strategy

**Built:** `users`, `auth_sessions`, `readiness_snapshots`, with Alembic migrations and the `vector` extension enabled by `infrastructure/postgres/init/01-extensions.sql`.

### 2.1 One database, one schema per phase of growth

All tables live in the `public` schema of one database. Contexts are separated by **table-name prefix and package ownership**, not by separate schemas, until a context is extracted. A separate schema per context is cheap to introduce later and costs a migration of grants only; it is not worth the friction of cross-schema migrations now.

| Context | Table prefix (designed) |
| --- | --- |
| Identity | `users`, `auth_sessions`, `role_grants` |
| Knowledge | `kn_` |
| Documents | `doc_` |
| Cards | `card_` |
| Questions and scenarios | `qs_` |
| Incidents | `inc_` |
| Labs | `lab_` |
| Architecture | `arch_` |
| Interview | `iv_` |
| Resume and JD | `rj_` |
| Behavioral | `beh_` |
| Evidence and evaluation | `ev_` |
| Readiness | `readiness_` |
| AI platform | `ai_` |
| Platform (jobs, outbox, stored objects, audit) | `jobs`, `outbox`, `stored_objects`, `audit_log` |

The existing three tables keep their names. Renaming them for the prefix scheme is not worth a migration.

### 2.2 Conventions

| Topic | Rule |
| --- | --- |
| Primary keys | UUID (`uuid.uuid4`), generated by the application. Client-supplied ids exist only as a separate idempotency column (`snapshot_id`), never as the primary key |
| Ownership | Every user-owned table has `user_id UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE` and an index starting with `user_id` |
| Time | `timestamptz`, UTC, set by the application clock that is passed in; `created_at` on every table |
| Enumerations | `varchar` plus a `CHECK` constraint, not a native enum type, so adding a value is a one-line migration |
| JSON | `JSONB` for **documents the database does not query by field** (a stored report, an event log, an LLM dimension map). Anything filtered, joined or constrained is a column |
| Versions | Versioned content has `(id, version)` as a unique pair; attempts reference both |
| Soft delete | None. Data deletion is real deletion by an account-level erasure job (section 9). Evidence is append-only, so erasure removes whole users, not single rows |
| Naming | `snake_case`, plural table names, `<table>_id` for foreign keys other than `user_id` |

### 2.3 Migrations

- Alembic is the only way the schema changes. The application never creates tables at start-up.
- A migration is one forward step, reviewed with the model change. Destructive changes (drop column, type change) use expand and contract across two releases.
- Migrations are the `alembic upgrade head` command, never code inside the API process. **Today** the API image runs it before starting uvicorn (the Dockerfile `CMD`), which is fine for one replica. With more than one replica it must move to a separate step before the rollout (a Compose service or a Kubernetes Job), because two replicas would race (ARCHITECTURE section 14).
- Tests run on SQLite for speed. Anything SQLite cannot represent (triggers, pgvector, partial indexes, `CHECK` with PostgreSQL functions) is tested against real PostgreSQL in CI; the model uses `JSON().with_variant(JSONB, "postgresql")` where both must work.
- **CI migration check (built):** the `migrations` job in `.github/workflows/ci.yml` starts `pgvector/pgvector:pg17`, runs `alembic upgrade head`, `downgrade base`, `upgrade head` again, then `alembic check` so the models and migrations cannot drift apart. Feature tests that need PostgreSQL itself (trigger behaviour, vector queries) are still to be written.

## 3. Append-only data

Append-only is a database property, not a convention (DAT-03 to DAT-08, PR-18).

| Table | Rule | Enforcement |
| --- | --- | --- |
| `readiness_snapshots` | Insert only | **Built.** A trigger rejects UPDATE; the application has no update or delete path |
| `ev_evidence` | Insert only | Designed. Same trigger pattern; corrections are new rows that reference the row they supersede |
| `ev_evaluations` | Insert only | Designed. Same |
| `*_attempts`, `card_reviews` | Insert while in progress, immutable once finished | Designed. Trigger on UPDATE of a finished row |
| `ai_usage`, `audit_log` | Insert only | Designed. Same |
| `jobs`, `outbox` | Updated (status) | Not append-only. They are operational state, not history |

The application role has no `DELETE` grant on append-only tables. Account erasure runs under a separate administrative role and is itself recorded in `audit_log` before the rows go.

## 4. Evidence storage

Detail of the model is in [DOMAIN_MODEL.md](DOMAIN_MODEL.md) section 5. Storage rules:

- `ev_evidence`: one row per (attempt, factor) with a unique constraint. Columns: `user_id`, `attempt_type`, `attempt_id`, `factor`, `score`, `origin`, `basis`, `evaluation_id`, `content_ref`, `occurred_at`, `recorded_at`. Index `(user_id, factor, occurred_at)` serves the readiness engine, which reads a user's evidence in time order.
- `ev_evaluations`: `subject_type`, `subject_id`, `evaluator_id`, `evaluator_version`, `basis`, `dimensions` (JSONB), `model_call_id` (nullable), `created_at`.
- `readiness_snapshots` keeps referencing evidence by **fingerprint** today, and gains an `evidence_ids` link table (`readiness_snapshot_evidence`) when evidence is stored server-side, so a snapshot lists exactly what it used (RDY-08).
- Replay (RDY-11, DAT-07): a recompute selects evidence `occurred_at <= T`, runs the engine at the stored config version, and inserts a new snapshot. It never edits one.

### 4.1 Outbox

A change that other contexts react to writes an `outbox` row in the same transaction. A worker marks rows processed. Delivery is at-least-once, so every consumer is idempotent. There is no event bus; see [ADR-0013](ADR/0013-evidence-store-and-domain-events.md).

## 5. Vector storage and retrieval

Decision: [ADR-0011](ADR/0011-retrieval-and-vector-storage.md). **Extension built; tables designed (phase 07).**

### 5.1 Tables

| Table | Columns that matter |
| --- | --- |
| `doc_chunks` | `id`, `document_id`, `user_id` (null for system content), `index_version`, `ordinal`, `heading_path`, `text`, `token_count`, `provenance_type`, `embedding vector(N)`, `embedding_model`, `embedding_model_version`, `created_at`, `tsv tsvector` |
| `doc_index_versions` | `id`, `document_id`, `chunker_version`, `embedding_model`, `dimension`, `state` (`building`, `active`, `retired`), `created_at` |

`N` is the dimension of the configured embedding model and is **fixed per index version**. Changing the model creates a new index version and a new set of chunks; it never converts vectors in place.

### 5.2 Indexing

- Index: HNSW (`vector_cosine_ops`) on `embedding`, created per index version via a partial index (`WHERE index_version = ...`) or a per-version column set, decided in the migration that creates the table.
- Full-text: a GIN index on `tsv`, so retrieval can combine keyword and vector scores (hybrid search).
- Filters first: `user_id` and `provenance_type` filters are applied in SQL **before** ranking. A user can never retrieve another user's chunks, because the owner filter is part of the single retrieval function and not left to the caller.

### 5.3 Retrieval function

One function in the Documents context, `search(actor, query, filters, k)`, is the only retrieval path. It:

1. Embeds the query through the P1 gateway (embedding purpose).
2. Runs hybrid search constrained by owner and filters.
3. Returns chunks with ids, provenance and scores; it returns no free text the caller did not request.
4. Records the query metadata (not the raw text) in `ai_usage`.

Retrieval quality is measured with a fixed question-to-chunk set in the golden-set suite ([AI_ARCHITECTURE.md](AI_ARCHITECTURE.md)).

### 5.4 Re-indexing

1. Create a new `doc_index_versions` row in `building`.
2. A worker chunks and embeds under the new version in batches, idempotently.
3. On completion the version flips to `active` and the old one to `retired` in one transaction.
4. Retired chunks are deleted after a grace period.

Retrieval reads the `active` version only, so a rebuild never serves a mixture.

## 6. Object storage and artifacts

Decision: [ADR-0009](ADR/0009-file-and-object-storage.md). **Designed.**

| Concern | Rule |
| --- | --- |
| Bucket layout | One private bucket. Key = `u/<user_id>/<object_id>` for user files, `sys/<kind>/<id>` for system artifacts. Key never contains the original filename |
| Metadata | `stored_objects`: `id`, `owner`, `key`, `size`, `content_type`, `sha256`, `original_name`, `state` (`pending`, `ready`, `quarantined`, `deleted`), `created_at`. The filename is data, not a path |
| Upload | Through the API: size and type checked before storing, SHA-256 computed while streaming, state `pending` until the parse job succeeds |
| Download | Through the API after an authorization check, or a short-lived presigned URL (minutes) |
| Content | Accepted types: PDF, DOCX, Markdown, plain text. Executables, archives and HTML are refused. Parsing runs in a worker with time, memory and output limits |
| Artifacts | Generated outputs (exports, reports) are stored the same way with an expiry and are re-creatable from the database |
| Scanning | A malware scan hook runs between `pending` and `ready`; ClamAV is the planned implementation. Until it exists, files are parsed but never served back to other users |
| Local | MinIO in Compose behind `--profile storage`. The same S3 client works against any S3-compatible service |

## 7. Redis

Nothing in Redis is authoritative. Uses, in the order they appear:

| Use | Key pattern | Expiry |
| --- | --- | --- |
| Celery broker and results | Celery-managed | Results expire; job truth is in PostgreSQL |
| Pub/sub for the WebSocket channel | `ws:user:<id>` channels | None (transient) |
| Shared login and registration throttles (replaces in-process counters) | `rl:<scope>:<key>` | The window length |
| Model response cache, **only** for deterministic, non-personal calls such as embeddings of seeded content | `llm:<hash>` | Days |
| Short-lived locks (one re-index at a time per document) | `lock:<name>` | Seconds |

Redis runs with persistence on locally so a restart does not lose queued messages, but the design does not rely on it. In production the `noeviction` policy is used for the broker database and keys always carry an expiry.

## 8. Job state

`jobs` rows are the record of background work (ADR-0008): `id`, `type`, `subject_type`, `subject_id`, `user_id`, `status` (`queued`, `running`, `succeeded`, `failed`, `cancelled`), `attempts`, `progress`, `error_code`, `created_at`, `started_at`, `finished_at`. A sweeper re-enqueues rows stuck in `queued` or `running` past a timeout, which is why a lost Redis message is a delay and not a loss.

## 9. Retention, erasure and backup

The spec is silent on these and TODO D-04 is open, so the table gives the **proposed defaults** the design is built to allow, not commitments.

| Data | Proposed default | Mechanism |
| --- | --- | --- |
| Evidence, evaluations, snapshots | Kept while the account exists | Append-only tables |
| Uploaded files and chunks | Kept until the user deletes the document | Delete job removes object, chunks and vectors, and logs it |
| Expired auth sessions | Purged after 30 days | Scheduled worker job |
| `ai_usage` | 13 months, then aggregated | Scheduled job |
| `audit_log` | 13 months | Scheduled job; export before purge if required |
| Account erasure | Removes all user rows and objects on request | Administrative erasure job, recorded in `audit_log` before rows go |
| Logs | 30 days | Log platform setting |

| Backup concern | Proposed |
| --- | --- |
| PostgreSQL | Nightly logical dump plus WAL archiving where point-in-time recovery is wanted. Local development has no backup beyond the Docker volume |
| Object storage | Versioned bucket and cross-location replication when hosted |
| Restore test | A restore into an empty environment is exercised before the first real user, and then each quarter |
| RPO / RTO | Not set. To be decided with D-04 |

## 10. Migration from browser storage to the API

Modules were built browser-first; the API takes them over **one module at a time** behind a repository interface, never by a big switch.

| Step | What happens |
| --- | --- |
| 1 | The module's repository interface already exists in the web app (the readiness snapshot repository is the pattern) |
| 2 | Add the context's tables, service and routes, with the isolation tests |
| 3 | A second repository implementation talks to the API. Signed-out users keep the browser one |
| 4 | On first sign-in the module offers a one-time import of local data. Items carry client ids so the import is idempotent. **Local data is not deleted by the import** |
| 5 | After a release in which the import has been available, the browser store becomes a cache that the API overwrites |

**Built:** readiness snapshots (steps 1 to 4, with the migration of local snapshots on sign-in). **Not started:** every other module. Saved resumes and job descriptions stay in the browser until the documents phase.

Order of migration follows evidence value: attempts and evidence first (phase 12 onward), then documents (phase 07), then cards, interview sessions and architecture designs.

## 11. Data classification

| Class | Examples | Handling |
| --- | --- | --- |
| Secret | Provider API keys, session tokens, password hashes, `SECRET_KEY` | Never logged, never in an API response; session tokens stored only as hashes; passwords as scrypt hashes |
| Personal | Email, name, resume text, job descriptions, runbooks, interview answers | Owner-only access; redacted before any cloud model call; erasable |
| Internal | Evidence, snapshots, usage ledger | Owner-only; aggregated only in anonymous form |
| Public content | Seeded questions, scenarios, patterns | Versioned in the repository |

Uploaded resumes and runbooks are treated as personal data. A privacy policy for them is an open item (D-04).
